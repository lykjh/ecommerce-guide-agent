# 技术方案与状态设计

版本：0.1.0｜状态：设计建议，商城契约待补

## 1. 编排与信任边界

使用现有 LangGraph 单 Agent。业务明确的路径采用固定节点；需要逐步取数的路径允许有限工具循环。编排、预算、状态更新在 Python 服务；商品业务、订单归属、登录认证仍由商城确定性代码负责。

```text
商城 UI → 商城认证入口 → Agent 服务
                         ├─ 对话状态 / 身份绑定 / 预算控制
                         ├─ 固定业务节点或有限决策循环
                         ├─ 工具执行器 → 商城业务服务
                         ├─ RAG → 有版本和适用范围的政策材料
                         └─ 回答 / 商品卡片 / 人工接管状态
```

具体网络拓扑和鉴权传递方式等商城资料补充后确定。必须满足：浏览器不能任意指定用户身份；Agent 服务和会话恢复入口均验证调用方；订单归属在商城服务每次查询时校验。会话 ID 本身不是访问凭证。

用户文本、历史消息、知识片段和工具中的自由文本均是不可信数据。模型只能提出候选动作，执行器校验允许能力、业务参数、身份、预算后才能调用。禁止任意 SQL、任意代码及任意 URL 执行工具。

## 2. 模型策略

沿用当前配置作为评测起点：qwen-flash 负责路由和条件提取，qwen-plus 负责需要组织说明的最终回答。这是已有项目配置的延续，不是对当前模型价格或效果的外部比较结论。

固定澄清、登录提示、权限拒绝、接口失败说明由确定性模板完成。简单事实可直接模板呈现，复杂推荐/对比再用回答模型。不对每句话额外调用模型做守卫；商品 ID、金额、状态优先程序校验。模型版本、生成参数和部署标识要记录到评测清单；实际供应商能力待核实。

重试、调用数、token、时间预算统一见 [06](06-budgets.md)，所有 LLM 调用包括路由、摘要、校验和重写均计数。

## 3. RAG 范围

RAG 负责政策、配送说明、使用说明，不作为实时价格、库存和订单数据库。资料记录来源、版本、生效/失效信息和适用范围。商品专属政策优先于泛化材料，前提是商城业务确认其适用性；冲突无法确定时转人工确认。

按语义完整段落切分，检索前约束可访问和适用范围，检索后保留可追踪证据。文件修改或删除必须清理失效索引。检索阈值由标注集校准，不假定某个向量距离天然代表正确匹配。

V1 不默认引入查询无限改写、知识图谱或多阶段重排；先评估召回不足类型再决定。

## 4. 会话状态

以下是逻辑状态，不是数据库 DDL 或对外 schema。

| 状态 | 含义 | 更新规则 |
| --- | --- | --- |
| 身份绑定 | 会话归属、游客/已登录、身份版本 | 可信入口更新；登录/退出/换号后重新绑定并清理敏感订单上下文 |
| 最近消息 | 当前会话原始对话窗口 | 按条数及 token 双重裁剪 |
| 历史摘要 | 较早对话偏好和未完成事项 | 辅助理解；不作价格、权限和订单证据 |
| 当前商品与候选列表 | 商品/规格 ID、展示顺序 | 每轮真实返回后更新；避免把列表位置当永久商品身份 |
| 已确认条件 | 品类、预算、用途、颜色等 | 区分用户明确值与模型推测；不能默默放宽硬约束 |
| 当前订单与候选订单 | 本人已查询的订单指向 | 换身份清除；实际查询仍重新授权 |
| 待澄清问题 | 正在等待的选择及上下文 | 回答后消耗；换话题可取消 |
| 推荐偏好 | 是否明确拒绝推荐 | 用户重新明确请求后才能解除 |
| 人工状态 | 机器人、排队、人工接管、结束 | 根据接待系统事实更新，模型不能自行宣布接管 |
| 本轮执行账本 | 工具结果、调用计数、deadline、退出原因 | 每次新请求建立；同请求重入不能清零预算 |

本地开发可继续使用 SQLite checkpoint；生产存储待并发、部署副本数和保留策略确定后选型。业务状态不等于模型聊天历史。

同会话消息按顺序处理；新请求不得与旧请求争抢更新状态。使用可跨部署实例生效的会话串行机制或版本冲突检测，具体实现待生产存储确定。断线/取消必须停止后续调度；新会话与不同用户不能共享工具缓存或订单状态。

## 5. 工具循环与退出

1. 解析问题与当前对象；必要信息缺失时直接澄清，结束本轮。
2. 选择固定路径，或让模型提出下一项允许能力。
3. 执行器检查身份、参数、剩余次数/token/时间和重复调用指纹。
4. 执行工具，将有界、脱敏的结果及业务状态写入账本。
5. 有新信息且确实需要下一步时继续；否则回答或澄清。
6. 输出前核验引用商品、金额、状态等关键事实；保存状态并结束。

重复指纹包含工具能力、规范化业务参数、可信身份作用域及本轮数据版本。相同成功查询在本轮复用，不跨用户复用订单结果。参数文本不同但业务含义相同也应识别；无法识别时仍受全局硬预算保护。

只有幂等只读查询的明确暂时性故障可重试。身份失败、权限失败、参数缺失、确定无结果不重试。人工请求结果不明进入核实/待确认，不把调用超时当作未创建成功。

无进展包括相同结果重复返回、没有新对象/证据、已经知道缺少同一参数。达到任一硬预算即停止调度，不用额外模型调用解释超预算，采用固定结束模板。

LangGraph recursion limit 作为最后保险；它按图执行步计数，不等同于工具轮数。最终数值应根据实际图的最长合法路径计算，不能随意以工具次数代替。

## 6. 输出与人工接管

商品卡片的 ID、链接、图片和价格来自工具结果，由程序组装。需要事实校验的回答在校验完成前不向用户流出；可先发送不含业务结论的进度信息。用户看见的流式文字不能在后台悄悄改写成另一份定稿。

用户请求人工时创建幂等接待请求。排队中可显示排队状态，默认停止主动导购；实际接管后机器人停止自动业务回复。无人在线返回真实离线/留言路径。恢复机器人必须由明确的接待状态变化或用户操作触发。

## 7. 现有代码迁移方向

- main_agent：补订单/人工分支及预算控制，保留图装配职责。
- router：增加必要上下文；未知意图不能一律当作商品咨询。
- memory：结构化对象状态、裁剪与身份切换隔离。
- tool/product：从 Mock 迁移到商城工具适配层，等接口补齐后设计。
- nodes：统一真实商品来源；商品校验基于 ID 和字段而非名称滑动窗口。
- rag：政策材料生命周期和来源追踪。
- web：保留内部调试用途；商城 UI 的通信协议稍后确定。

本节是施工方向，当前没有执行上述改动。
