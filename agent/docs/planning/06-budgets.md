# 成本、限流与执行预算

版本：0.1.0｜状态：建议初始值，待模型和商城延迟实测后评审

本文件是数值预算唯一来源。下列配置尚未实现，不是供应商模型能力或价格声明。

## 1. 本轮共享硬预算

“本轮”指一条用户请求的全部工作，包括路由、抽取、检索决策、回答、守卫、摘要、修复及重试。预算是上限而非必须用满的流程配额。

| 项目 | 初始上限 | 计数规则 |
| --- | --- | --- |
| 工具决策轮数 | 4 | 每次模型决定后续工具动作计一轮 |
| 工具实际调用尝试 | 6 | 每个工具及其重试各计一次；并行也分别计数 |
| LLM 调用尝试 | 8 | 路由、摘要、重试、修复等全部计入 |
| 同逻辑查询重试 | 1 | 仅幂等只读查询的暂时性故障 |
| 回答或解析修复 | 合计 1 | 两种修复共用一次额度，且必须仍有其他预算 |
| 单普通查询尝试 | 5 秒 | 不能超过剩余整轮时间；超时后取消等待 |
| 单 LLM 尝试 | 10 秒 | 同样受整轮 deadline 限制 |
| 整轮 deadline | 30 秒 | 从服务接纳请求起算，包含排队和所有尝试 |
| 本轮 token 总量 | 24,000 | 所有模型尝试输入+输出累计，失败尝试亦纳入估计 |
| 单次模型输入 | 8,000 token | 含系统提示、工具描述、状态、历史和证据 |
| 单次模型输出 | 1,200 token | 决策/抽取可更小，不默认用满 |
| 最终回答保留额度 | 6,000 token、1 次 LLM、5 秒 | 下一次探索会侵占保留额度时停止探索；不足则固定模板结束 |

供应商实际输出限制和 tokenizer 支持待核实。调用前按输入估计+输出上限预留 token，完成后按 usage 结算；并行调用原子预留，不能各自看到同一份剩余预算。usage 缺失使用保守估计并标注，不记零成本。

金额预算与 token 预算不同：模型输入、输出、缓存、embedding 可能分别计价，未拿到计费信息前不写虚构人民币价格。生产须补每日金额上限和模型价目版本。检查预算与预留应原子执行，避免并发超额。

## 2. 请求类型软目标

这些是评测起点，用来发现浪费，不代替上述硬上限。

| 请求 | 模型策略 | 累计 token 软目标 |
| --- | --- | --- |
| 寒暄/澄清 | 轻量路由和简短回复，能模板就模板 | ≤3,000 |
| 简单商品/政策问答 | 轻量抽取，必要时回答模型 | ≤8,000 |
| 推荐/对比 | 轻量决策，回答模型组织证据 | ≤16,000 |
| 订单查询 | 轻量对象解析，优先模板回复 | ≤6,000 |
| 人工请求 | 明确请求直接进入受控流程 | ≤2,000 |

明确动作可减少路由调用，但不能跳过身份和权限检查。历史优先保留最近 8 条消息，再按 token 裁剪；摘要目标 ≤600 token。证据总目标 ≤3,000 token；超长时选择相关字段/片段，不能截断关键政策条件或把截断结果当完整列表。

摘要更新也计预算；预算不够时保留上版摘要并裁剪旧原文，下轮按需澄清，不在本轮结束后偷偷继续付费任务。

## 3. 限流初始建议

| 维度 | 初始规则 | 说明 |
| --- | --- | --- |
| 已登录用户 | 滚动 60 秒最多 20 请求 | 多会话共享用户限额 |
| 游客会话 | 滚动 60 秒最多 10 请求 | 配合可信 IP 限制，不单靠可重建会话 |
| 来源 IP | 滚动 60 秒最多 60 请求 | 仅信任可信网关解析的来源；需评估共享出口误伤 |
| 同会话运行 | 最多 1 个请求 | 后续请求返回忙碌提示，不无界排队 |
| 单用户运行 | 最多 2 个请求 | 避免多会话绕过并发限制 |
| Agent 部署全局 | 最多 10 个运行请求 | 所有实例共享额度，超出返回忙碌，待压测调整 |

多维度同时检查，超任一限额即拒绝新工作；限流拒绝不调用模型。身份无效不能降为游客来继续查单。具体网关响应协议、限流存储实现和业务错误码留待接口阶段确定。

所有限流数值在上线前要结合访问规模、供应商配额及人工接待能力复核；压测须覆盖共享 IP、同用户多会话、跨实例和临界窗口。

## 4. 降级顺序

1. 输入过长：提示缩短或补充核心问题，不盲目截断成改变语义的请求。
2. 缺参、无权限、未登录：直接澄清或说明，不重试。
3. 可重试只读故障：在次数、deadline 和保留额度允许时最多一次；遵守下游等待要求，剩余时间不足则直接结束。
4. 模型不可用：已有确切业务结果可模板展示；否则说明未完成。第一版不做未经评测的自动换模型。
5. 工具不可用：不拿知识库代替实时价格和订单；提供重试或真实人工路径。
6. 达到预算或无进展：停止全部新调度，固定模板说明已确认/未完成项。
7. 人工创建结果未知：保持待确认状态并按接待系统能力核实，禁止盲目重复创建。

重试放在一个明确的执行层。供应商 SDK、HTTP 客户端和图节点内部重试应关闭或统一纳入预算，避免多层重试相乘。取消后停止排队和下一步调度；下游无法撤回的请求要记录，并禁止迟到结果覆盖新状态。

## 5. 成本评估与待补

每请求估算成本 = 各模型实际输入/输出用量 × 对应价格 + embedding/其他付费工具成本，缓存命中仅按供应商可核实计费规则折算。

待补：供应商价格版本、币种、每日预算金额、预期日请求量、峰值并发、模型配额、可接受的每请求成本目标。报告均值与 p95，不只报告平均 token。尚未确定日金额上限前，不宣称已有完整生产成本防护。

## 6. 商城下游与数据库保护（已确认纳入 V1）

Agent 通过商城受控接口访问业务数据，不直连业务库执行模型生成的 SQL。一次工具调用可能触发多个接口请求，一个接口也可能执行多条 SQL，因此工具次数不能当作数据库查询次数。

- 分开计数：工具尝试、实际商城请求（含重试、分页和详情展开）、商城侧 SQL。工具内部不得隐藏无上限的分页或逐项详情查询。
- 为每轮实际商城请求设置独立上限，并为整个 Agent 部署设置商城请求速率和在途并发上限；所有实例共享约束。具体值待接口调用展开情况和压测确定，上线前必须填实。前文的 Agent 请求并发上限不能替代下游并发上限。
- 每次实际下游发送前检查预算并获取额度；满额返回忙碌或部分结果，不无限排队。限流、过载响应不立即重试；持续故障时停止新查询并降级，恢复条件由商城承载数据确定。
- 本轮相同成功查询复用。商品详情尽量一次取得必要字段；对比在接口支持时批量获取。候选数、单页大小、翻页次数、单次对比数量在接口确认后设上限，禁止扫描全库或无界拉取历史订单。
- 优先复用商城现有缓存。描述、规格、政策与价格、库存分别制定有效期及失效规则；交易以商城结算校验为准。订单结果不跨用户共享，缓存不能跳过商城归属校验。
- 客户端超时不证明下游 SQL 已停止。记录未确认终止的请求，结合商城侧超时/取消和服务端在途指标限制重试，避免客户端释放额度后不断叠加后台查询。

不预先引入 Redis、读副本或搜索集群。先测既有接口和缓存能力，只有测量证明瓶颈后再评审改造。

粗估新增 SQL 速率可按“用户提问速率 × 每轮实际商城请求数 × 每个请求平均 SQL 数”计算；缓存命中、批量、重试均影响结果，最终以商城测量为准。Agent 自身的会话/checkpoint 写入也需计入其实际存储的负载评估。
