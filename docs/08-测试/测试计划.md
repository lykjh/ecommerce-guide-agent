## 1. 两层测试

确定性层验证：权限、参数校验、会话隔离、预算、超时取消、幂等、日志脱敏和指标计数。使用固定模型替身与工具 fixture，故意输出重复调用、无效动作等，以证明程序不依赖模型自律。

Agent 层验证：意图、对象解析、工具选择、条件语义、证据使用、最终回答。固定业务数据，使用真实模型评测。不能只断言回复中出现关键词，也不能只用 LLM 裁判判断权限和金额是否正确。

## 2. 用例结构与来源

每条用例包含：稳定 ID、需求 S/T 引用、类别、难度、单轮/多轮、身份条件、初始会话状态、输入序列、工具 fixture、允许调用轨迹、禁止动作、回答事实、终止条件、指标标签、Prompt 版本、数据版本。

允许多个等价轨迹，例如已持有可信商品 ID 时可直接详情查询；不得强制模型复述唯一固定句子。涉及硬权限或缺失参数时，禁止动作必须明确。

来源为业务人员构造、经授权脱敏的真实问题、边界/对抗样本。当前没有真实流量样本，首批均为人工构造。真实用户文本经授权、去标识化后才能进入评测；不保留完整手机号、地址、凭据。

按咨询、筛选推荐、对比、政策、订单、人工、闲聊澄清分类，交叉覆盖多轮、省略、拼写、混合问题、工具故障、提示词注入。训练式调优集与验收留出集分开，同一对话的改写不能分到两边造成泄漏。

## 3. 样本规模与运行

- 商城接入专项MA01–MA25及F01–F15人工数据设计见[测试用例](测试用例.md)，各验证层次独立记录，不把设计数量当通过数。
- 首批 [E01–E24](测试用例.md) 是开工种子集，可用于编写 fixture；尚不是足以证明目标准确率的验收集。
- 发版前目标至少 200 个业务样本，每个核心业务类别至少 20 个；其中至少 50 个多轮样本。另设至少 40 个安全/终止性挑战样本，单独报告，不混入总体平均掩盖失败。
- 首批种子样本允许与最终集合重叠，但已用于调优的样本不可再冒充独立留出样本。
- 发版全量真实模型运行 3 次，分别报告每次通过率、最差值及波动；各次均应通过硬门槛。
- 固定模型部署标识、温度等参数，记录 token、调用轨迹、Prompt hash、代码提交、数据 fixture hash。供应商不支持 seed 时如实记录，不宣称完全可复现。

## 4. 指标定义

| 指标 | 分子 / 分母或计算方式 |
| --- | --- |
| 意图/下一动作正确率 | 满足标注下一动作的样本数 / 可判定样本数；当前顺序复合请求以已约定的第一任务为下一动作，不把后续未执行任务算完成；完整任务覆盖另报 |
| 工具轨迹正确率 | 能力选择、参数语义、权限、依赖顺序、结束条件全部正确的样本数 / 需决策工具行为的样本数；应不调用却调用也计错 |
| 多轮对象解析正确率 | 对象选择或必要澄清正确的样本数 / 含指代或省略的样本数 |
| 无依据事实率 | 无授权证据支持或与证据冲突的可核实业务事实数 / 输出的全部可核实业务事实数 |
| 正确拒绝率 | 正确拒绝且无泄露的请求数 / 应拒绝请求数 |
| 误拒率 | 无正当原因拒绝的合法请求数 / 合法请求数；必要澄清与登录引导不算误拒 |
| 任务完成率 | 满足全部任务目标的样本数 / 具备完成前提的样本数；不能通过少答降低幻觉率 |
| 调用与 token | 每请求全部尝试总和，含失败重试、摘要、修复；token 不可用时报告未知比例和估计值 |
| 延迟 | 请求开始到首个有效答复、到最终结束；进度提示不冒充有效答复，分别报 p50/p95 |

建议目标值见[需求规格说明书](../02-需求/需求规格说明书.md)，实际执行预算见[工程设计](../04-工程/工程设计说明书.md)。分母为零时记 N/A，不记 100%。标注有争议的样本先由业务人员复核，不静默排除；报告排除数量与原因。初始任务完成率目标 ≥90%，同时满足准确性和安全门槛。

金额、商品 ID、订单状态、工具次数由程序校验；语义和说明充分性由人工 rubric 评审，模型裁判只辅助。固定安全集任一越权泄露、伪造订单金额、重复建单或超预算继续执行均阻断发布。

## 5. 频率与产物

| 触发 | 必跑范围 |
| --- | --- |
| Prompt 修改 | 关联用例 + 安全集 + 终止性集；公共/路由/约束变更全量 |
| 工具、权限、状态、预算修改 | 对应确定性回归 + 关联 Agent 用例；身份隔离改动全安全集 |
| 模型或生成参数修改 | 全量真实模型评测 |
| 每日回归 | 固定业务样本 + 新增线上失败样本；预算允许时跑全量 |
| 发版前 | 全量两层测试、留出集、重复运行、监控脱敏检查 |

每日回归是未来工程要求，本轮没有创建自动化任务。实际启用前须确定运行环境、执行预算与负责人。

每次报告保留：run ID、环境与版本、样本数、分类结果、原始断言、脱敏 trace 引用、token/成本、失败归因、与基线差异、发布结论。代码测试通过和真实模型评测通过分别陈述。

## 6. 数据库影响验收（上线必需）

在隔离测试环境使用固定数据规模及相同商城背景流量，对比关闭 Agent 与叠加 Agent 流量的结果。分别覆盖正常负载、峰值、冷/热缓存、复杂筛选、多商品对比、多轮追问、下游变慢与故障恢复。涉及下单使用测试订单，不对生产执行压力测试。

| ID | 测试 | 必须验证 |
| --- | --- | --- |
| DB01 | 关闭/开启 Agent 对照 | 商品浏览与下单的 p95、错误率、吞吐，以及 SQL 速率、慢查询、连接池等待和数据库资源变化 |
| DB02 | 重复查询与批量展开 | 所有内部请求/尝试计预算，分页和详情展开有界；未来引入同轮复用时再验证重复查询不重复访问，当前不得以不存在的缓存宣称通过 |
| DB03 | 多实例并发与速率 | 下游共享额度不被实例数放大；满额时有界退出；不会挤占商城至超出约定服务目标 |
| DB04 | 下游超时/过载 | 无重试风暴；客户端停止后核实商城侧残留查询；故障恢复不会瞬间放开积压任务 |
| DB05 | 缓存与身份 | 价格库存满足约定时效；权限检查不被缓存绕过；跨用户不复用订单结果 |
| DB06 | 状态存储 | checkpoint/消息写入的耗时、锁等待、存储增长与清理符合目标 |

执行前冻结：背景流量和数据量、预热/持续时间、目标 Agent 流量、商城现有 SLO、允许的延迟/错误率增量、数据库资源与连接池安全水位、工程文档中待补的下游额度。阈值未确定时只能记录测量结果，不能判定通过。

通过条件：DB02–DB05中与冻结部署/功能适用的确定性保护断言全部通过；未启用缓存/多实例的项目明确N/A并说明理由，不冒充该能力已实现，DB01/DB06 在冻结的业务与容量阈值内；不以 Agent 自身响应正常替代商城正常。超过任一硬阈值则降低 Agent 查询额度或修复接口后重测，不能直接提高阈值掩盖回归。

## 8. 执行入口与环境

从项目根目录运行，使用现有虚拟环境和Node.js（前端测试已在24.19.0验证），不在此文档执行安装或在线调用：

```powershell
.\.venv\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -p "test_*.py"
.\.venv\Scripts\python.exe -B -X utf8 -m unittest tests.test_http_ui -v
node tests/http_ui.test.mjs
.\.venv\Scripts\python.exe -B -X utf8 -m unittest tests.v1.i.test_seed_dataset
```

离线测试使用临时数据库与固定模型/商城替身。写日志目录及创建测试子进程需要运行环境权限；权限不足是环境失败，不应通过改业务代码掩盖。不要清理真实chat_memory.db或重建用户向量库来使测试通过。

真实模型脚本、实际商城请求和负载验证分别执行、分别记录费用和范围。历史live脚本并不等于当前验收入口全部适配最新契约；调用前先核对脚本目标、环境、额度、数据及代码版本。禁止在未冻结环境和停止线时对生产压测。

## 9. 入口、退出与缺陷处理

开始测试前：冻结需求/接口版本，准备可复现fixture，确认身份和环境、模型部署、Prompt及数据hash，记录代码提交或工作区状态；涉及费用和压力先明确预算与执行范围。

失败先区分业务缺陷、过时断言、测试自身或环境问题。保留原始失败，再以最小复现定位；禁止删除关键断言、缩小样本分母或修改正确业务来凑绿。修改后运行针对性测试；核心身份/状态/预算变更补相应全量回归。资料不足、业务未实现为blocked，不计pass。

发布退出条件是所有适用门槛通过且阻塞事项处理完毕；缺失的真实权限、政策、人工、语义或容量证据不能用Mock通过抵消。整体验收与交付清单分别记录实际范围和未完成项。

## 10. A-1.0阶段验收口径（用户已确认）

本节是审查测试编写用例和执行方案的依据，不代写具体用例。仅验商品相关咨询、推荐、对比、概览、分类澄清、多轮条件变化、失败和注入；关联A-R01–A-R10。保留既有预算、取消、匿名隔离及相关窗口回归，不纳入订单/政策/人工成功路径或生产容量结论。

| 门槛 | 执行和判定口径 |
| --- | --- |
| 确定性行为 | 所有本阶段适用检查100%通过；必须覆盖已确认分类/规格/多轮/分页/预算规则，不能把未实现项标N/A规避 |
| 商品事实硬门槛 | 已执行验收样本中虚构商品、错误价格、跨SKU拼接、将未核实条件说成满足均为0例；价格按响应时点及同SKU证据核对，不用下单后的新价格倒判旧回复 |
| 语义质量 | 总体正确率≥95%，每类≥90%；按预先标注的意图、分类选择、多轮条件理解判定，不以回复出现关键词作为唯一依据；一条样本的所有适用语义目标满足才计正确 |
| 失败与范围表达 | 无匹配/资料不足/接口失败区分，批次范围诚实；硬条件不自行放宽。任一违反已确认规则不能被总体语义分数抵消 |
| 真实证据 | 固定数据验证与真实商城小样本各有结果；真实颜色必须有多规格SKU样例；数据缺失记阻塞，不能以模拟数据替代实证 |

总体正确率分子为语义目标全部正确的样本数，分母为冻结的本阶段可判定语义样本数；按场景类别分别计算相同口径，多轮样本按完整输入序列判定，不能把成功轮拆开稀释失败。审查测试执行前冻结分类、样本分配、允许等价行为及判分依据；分母为0记未验证，不记100%。基础设施失败保留并单独统计；若语义无法判定，报告排除原因及覆盖缺口，补足后才作阶段达标判定。

沿用第3节评测与留出原则，本阶段只选商品相关场景；完整V1的200业务/40安全目标不是本阶段已批准的独立样本总数。阶段样本总数及各类分配由审查测试提交执行计划确认，不在此补造数值。已调优样本不冒充独立留出集；固定样本、模型、Prompt、数据和代码版本，沿用发版全量重复3次的报告方法，各次满足硬门槛和本阶段语义阈值。

执行前条件：以商城接口v1.3中核对的shiwushop源码为契约，确认实际服务与该工程版本一致；再确认目标商城版本/地址、可用分类和多规格样例、隔离会话存储、真实模型及调用费用范围；这些条件影响在线执行，不阻止离线用例设计。不得未经确认扫描全分类或对共享商城压测。实现变化引起的现行全量离线回归须实际发现并执行，历史157项或现行声明数量不能代替本次结果。

输出仅需现有验收报告及原始证据：版本、范围、样本分母、分层/分类结果、硬失败、阻塞、调用/用量和实际限制。Tech Lead界定要求和标准，审查测试独立设计用例；本次文档定稿没有执行任何验收。
