## 1. 两层测试

确定性层验证：权限、参数校验、会话隔离、预算、超时取消、幂等、日志脱敏和指标计数。使用固定模型替身与工具 fixture，故意输出重复调用、无效动作等，以证明程序不依赖模型自律。

Agent 层验证：意图、对象解析、工具选择、条件语义、证据使用、最终回答。固定业务数据，使用真实模型评测。不能只断言回复中出现关键词，也不能只用 LLM 裁判判断权限和金额是否正确。

## 2. 用例结构与来源

每条用例包含：稳定 ID、需求 S/T 引用、类别、难度、单轮/多轮、身份条件、初始会话状态、输入序列、工具 fixture、允许调用轨迹、禁止动作、回答事实、终止条件、指标标签、Prompt 版本、数据版本。

允许多个等价轨迹，例如已持有可信商品 ID 时可直接详情查询；不得强制模型复述唯一固定句子。涉及硬权限或缺失参数时，禁止动作必须明确。

来源为业务人员构造、经授权脱敏的真实问题、边界/对抗样本。当前没有真实流量样本，首批均为人工构造。真实用户文本经授权、去标识化后才能进入评测；不保留完整手机号、地址、凭据。

按咨询、筛选推荐、对比、政策、订单、人工、闲聊澄清分类，交叉覆盖多轮、省略、拼写、混合问题、工具故障、提示词注入。训练式调优集与验收留出集分开，同一对话的改写不能分到两边造成泄漏。

## 3. 样本规模与运行

- 商城接入专项MA01–MA25及F01–F15人工数据设计见[测试用例](测试用例.md)，各验证层次独立记录，不把设计数量当通过数。
- 首批 [E01–E24](测试用例.md) 是开工种子集，可用于编写 fixture；尚不是足以证明目标准确率的验收集。
- 发版前目标至少 200 个业务样本，每个核心业务类别至少 20 个；其中至少 50 个多轮样本。另设至少 40 个安全/终止性挑战样本，单独报告，不混入总体平均掩盖失败。
- 首批种子样本允许与最终集合重叠，但已用于调优的样本不可再冒充独立留出样本。
- 发版全量真实模型运行 3 次，分别报告每次通过率、最差值及波动；各次均应通过硬门槛。
- 固定模型部署标识、温度等参数，记录 token、调用轨迹、Prompt hash、代码提交、数据 fixture hash。供应商不支持 seed 时如实记录，不宣称完全可复现。

## 4. 指标定义

| 指标 | 分子 / 分母或计算方式 |
| --- | --- |
| 意图/下一动作正确率 | 满足标注下一动作的样本数 / 可判定样本数；当前顺序复合请求以已约定的第一任务为下一动作，不把后续未执行任务算完成；完整任务覆盖另报 |
| 工具轨迹正确率 | 能力选择、参数语义、权限、依赖顺序、结束条件全部正确的样本数 / 需决策工具行为的样本数；应不调用却调用也计错 |
| 多轮对象解析正确率 | 对象选择或必要澄清正确的样本数 / 含指代或省略的样本数 |
| 无依据事实率 | 无授权证据支持或与证据冲突的可核实业务事实数 / 输出的全部可核实业务事实数 |
| 正确拒绝率 | 正确拒绝且无泄露的请求数 / 应拒绝请求数 |
| 误拒率 | 无正当原因拒绝的合法请求数 / 合法请求数；必要澄清与登录引导不算误拒 |
| 任务完成率 | 满足全部任务目标的样本数 / 具备完成前提的样本数；不能通过少答降低幻觉率 |
| 调用与 token | 每请求全部尝试总和，含失败重试、摘要、修复；token 不可用时报告未知比例和估计值 |
| 延迟 | 请求开始到首个有效答复、到最终结束；进度提示不冒充有效答复，分别报 p50/p95 |

建议目标值见[需求规格说明书](../02-需求/需求规格说明书.md)，实际执行预算见[工程设计](../04-工程/工程设计说明书.md)。分母为零时记 N/A，不记 100%。标注有争议的样本先由业务人员复核，不静默排除；报告排除数量与原因。初始任务完成率目标 ≥90%，同时满足准确性和安全门槛。

金额、商品 ID、订单状态、工具次数由程序校验；语义和说明充分性由人工 rubric 评审，模型裁判只辅助。固定安全集任一越权泄露、伪造订单金额、重复建单或超预算继续执行均阻断发布。

## 9. 入口、退出与缺陷处理

开始测试前：冻结需求/接口版本，准备可复现fixture，确认身份和环境、模型部署、Prompt及数据hash，记录代码提交或工作区状态；涉及费用和压力先明确预算与执行范围。

失败先区分业务缺陷、过时断言、测试自身或环境问题。保留原始失败，再以最小复现定位；禁止删除关键断言、缩小样本分母或修改正确业务来凑绿。修改后运行针对性测试；核心身份/状态/预算变更补相应全量回归。资料不足、业务未实现为blocked，不计pass。

发布退出条件是所有适用门槛通过且阻塞事项处理完毕；缺失的真实权限、政策、人工、语义或容量证据不能用Mock通过抵消。整体验收与交付清单分别记录实际范围和未完成项。

### 11.3 失败处理和总验收

1. 发现跨账号泄露、伪造商品/订单/金额、跨SKU拼接、超预算仍调度、重复接待建单等硬失败，停止受影响批次并留脱敏证据，不能用平均正确率抵消。
2. 审查测试写期望/实际、依据ID、复现、版本和影响；总控将问题退给唯一开发负责人。开发修复后交新哈希及关联回归，独立人员复验；原失败保留。
3. 所有适用分项通过、完整V1建议门槛已确认且达标、必需证据可访问、运维接收后，总控才能在验收报告汇总“完整V1通过”。发布/公网部署仍需单独批准。
4. 若只交公开商品或身份阶段，必须明确阶段名、限制及未完成业务；缩范围须用户确认，不把B/D/E缺依赖默认为剔除，不把文档完成当项目完成。

## 2026-11-12 DS-1 定向验证要求

适用明确品类首轮询价及多轮查询。必须从空分类状态开始，并让分类接口存在正常非空数据；不能预置关键词模式或让用户追加“按关键词搜索”来绕过首轮验收。首轮必须查询商品、核实SKU、给出本批结果，分类请求为0。
离线覆盖预算继承/取消、换品类清游标、旧待选状态退出、保留可信已选范围、无匹配、显式浏览及导航失败。真实模型通过商城代理连续执行询价→预算收紧→不限→换品类→下一批；逐条核对价格、SKU可售状态、续页不重复及每轮工具轨迹。不得因旧测试要求首轮分类而恢复旧业务设计。结果另见开发证据，不等同独立验收。
