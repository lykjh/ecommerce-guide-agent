# 身份与会话归属实现设计

版本：C-D1.0｜日期：2026-11-04｜适用：身份阶段C；实现设计基准不变；2026-11-04已核对C-fix-20261104-2及C-1离线独立复验通过证据，真实身份/宿主联调未完成。已确认的业务选择为同域不同路径、身份变化新会话。本文给出总控的具体实现方案，不把架构选型留给开发；不授权编码、在线调用或跨区访问。

接口唯一来源：[Agent服务接口第7节](D:/desktop/PythonProject/docs/03-接口/Agent服务接口.md)。施工入口：[C-0任务](D:/desktop/PythonProject/docs/05-施工进度/任务单/C-0-身份与会话归属方案.md)。下列“必须”约束本方案的实现与验收，不表示用户已批准部署参数或真实环境操作。开发的原依据版本及哈希保留在交付快照；本次仅更新状态，行为契约不变。

## 1. 选择与理由

保留FastAPI、现有Bearer聊天凭证、LangGraph和SQLite。增加HTTP入口的商城身份确认与持久归属记录；图内仍只接收随机thread_id，不增加鉴权节点，不把用户ID当thread_id。这样两个聊天不会因属于同一个用户而合并，现有记忆、预算和业务节点无需改造。

身份来源固定为商城GET /users/me；Agent不实现登录，不信任前端userId或模型输出。查询在创建会话、发送消息时进行，不在每个节点、每个token检查；不加身份缓存或重试。代价是携商城Cookie的每个有效请求新增一次商城查询，换取失效状态在下一次请求被确认。

归属同时绑定用户ID和登录会话指纹。只存用户ID不能区分同账号退出后重登。已静态核对商城LoginServiceImpl登录成功调用request.changeSessionId()；登录会话指纹取该Cookie的HMAC，不能保存原始Cookie。此依赖必须用真实重登验证，不能由单元测试代替。

本阶段公开商品和闲聊可用，订单/物流仍不开放。身份变化新会话不等于删除旧数据库记录；不增加历史列表、恢复入口、跨会话画像或定时清理任务。

## 2. 请求链与校验位置

创建会话：来源检查 → 确认商城身份 → 生成现有随机ID → 事务写入归属记录 → 返回签名token。写入未成功不得返回token；不进入图、不调用模型。

发送消息：来源检查 → 校验现有message/schema和Bearer签名 → 按session_id查归属 → 确认商城身份 → 比较归属 → 调用现有stream_reply(message, session_id, request_id)。所有入口条件通过前不读checkpoint、不建立SSE、不调用模型。FastAPI各依赖的实际求值顺序不得破坏此边界；请求体和签名各自只校验一次。

同一请求的request_id在HTTP入口产生，贯穿身份查询、归属校验和已有图日志。身份模块返回已校验的可信对象，HTTP比较后只向图传随机会话ID。后续节点、memory、商品工具不重复鉴权或检查身份字段，不在AgentState中增加Cookie或账号资料。

不有效的Bearer/不存在的归属记录直接拒绝，不先查询商城。归属存在但身份不同统一返回SESSION_IDENTITY_CHANGED，不泄露该会话属于谁，不改写原归属，不自动把消息提交到新身份。

## 3. 身份模块及上游边界

新增D:/desktop/PythonProject/agent/identity.py，负责商城身份确认、可信身份类型和登录指纹；它不依赖业务节点，不调用LLM。沿用项目标准库urllib的HTTP方式及现有配置读取，不新增HTTP客户端框架。

可信对象字段：kind取guest或user；user_id为十进制字符串或null；login_fingerprint为64位十六进制字符串或null。guest后两项均为null；user两项必有。此结构只在身份解析边界构造，下游不重复Pydantic校验。

| 输入/结果 | 处理 |
| --- | --- |
| 请求没有MALLSESSION Cookie | 构造guest，不访问商城 |
| 请求有MALLSESSION | 只转发这一项到MALL_BASE_URL对应的GET /users/me；不转发完整Cookie、Agent Authorization、客户端userId或任意客户端目标URL |
| HTTP 200，包络code为整数200，data.id为正整数 | 解析为user；Java Long ID在Python边界转十进制字符串，避免后续JS精度问题；不消费username、role、phoneMasked |
| HTTP 401且包络code为整数401 | 确认为guest；这是未登录/登录失效，不是依赖故障。原user会话随后因归属不同被拒绝；新会话可按guest创建 |
| HTTP 403 | IDENTITY_UNAVAILABLE；不得猜测为guest或绕过 |
| 超时、连接失败、429、5xx、3xx | IDENTITY_UNAVAILABLE；不跟随重定向、不重试、不自动降级guest |
| 其余HTTP状态、错误JSON、成功/401包络不匹配、id缺失/布尔/浮点/字符串 | IDENTITY_BAD_RESPONSE；不容忍性猜测或调用模型修复 |

上游包络按code/message/data解析一次；message不回显上游正文；id才是此阶段必需的业务字段，其他额外业务字段允许忽略。原始Cookie只在本次请求及其在途HTTP操作中存活，不进入日志、异常正文、返回体、归属库或checkpoint。上游Set-Cookie不转发、不保存，不使用共享CookieJar。MALL_BASE_URL只来自服务器配置，禁止自动跳转，避免把凭据带到其它目标。

login_fingerprint = HMAC-SHA256(AGENT_SESSION_SECRET, UTF-8编码的“mall-login\0”与原始MALLSESSION值拼接)。固定前缀用于区分聊天签名用途。guest不绑定登录前的CSRF会话Cookie；否则获取CSRF也会不必要地打断游客聊天。匿名聊天token仍是持有者凭证，不能据此宣称游客可相互转交token而仍保持私密。

## 4. 持久归属与升级

新增D:/desktop/PythonProject/agent/session_store.py，只负责归属记录的创建、读取和连接生命周期，不读取聊天内容。使用已经安装的aiosqlite；若作为直接导入使用，在requirements.txt显式固定当前环境已安装版本，不升级依赖。

归属库路径由现有path.db解析后的路径以with_suffix('.sessions.db')派生，例如D:/desktop/PythonProject/chat_memory.sessions.db。独立于LangGraph库，避免争用现有checkpoint事务锁；不另加一套可配置路径。测试传入测试临时路径，不写项目真实库。该库属于运行数据，遵循现有数据库忽略规则，不提交Git。

表名chat_session_owners：

| 字段 | SQLite类型/约束 | 用途 |
| --- | --- | --- |
| session_id | TEXT PRIMARY KEY NOT NULL | 现有32位随机聊天ID；同时为图thread_id |
| owner_kind | TEXT NOT NULL，guest/user | 归属类型 |
| user_id | TEXT，可空 | user为正整数十进制字符串；guest为null |
| login_fingerprint | TEXT，可空 | user为64位HMAC；guest为null |
| created_at | INTEGER NOT NULL | UTC Unix秒，服务端生成 |

以数据库CHECK保证guest/user字段组合；主键和组合约束承担存储完整性，不在每个调用方反复判空。记录创建后不换绑，不新增last_seen等每轮写入；聊天只按主键读一条。连接在FastAPI lifespan打开/关闭，使用单连接、一个异步锁串行执行归属事务，事务范围只含SQL，不跨商城HTTP或LLM调用。

SQLite连接busy timeout为1秒；锁等待加操作的入口等待上限为1秒。捕获明确的SQLite/超时错误转SESSION_STORE_UNAVAILABLE，不吞错、不自动重试。取消后完成必要的提交/回滚和连接清理再释放锁，不让未结束事务与下一请求交错；不能把事务清理计为业务成功。

升级创建新表即可，不回填旧token、不扫描/删除旧checkpoint。签名有效但找不到归属的旧token返回401 INVALID_SESSION。新建会话使用新随机ID。重启保持同一签名密钥、归属库和记忆库时，且商城登录仍有效，允许原token继续；更换密钥会使原token失效。

两个库不是跨库事务：仅创建归属时不创建图历史；用户未发消息或响应丢失留下空会话归属属于允许结果。数据库损坏/缺失不得通过从旧聊天推断身份来恢复访问。升级和回滚都先备份两个库；启用身份后的环境不得直接回滚到只验签名的旧HTTP实现，否则重新开放无归属校验的访问。

## 5. 同域路径与来源保护

约定公开前缀/assistant/，上游FastAPI仍用/api/sessions、/api/chat和/ui/*。代理去掉/assistant前缀转发到独立Agent；应用使用Uvicorn --root-path /assistant；/assistant重定向到/assistant/。后端/users/*继续由商城处理；本次已确认的Vite宿主在浏览器使用/api/users/*，由其原代理剥/api后转发，不能将浏览器商城/api路径交给Agent。前缀可由代理和root_path一起调整，不改业务接口、不写死部署域名。

index.html把绝对/ui资源地址改为./ui/...。chat.js用自身import.meta.url的上一级目录推导应用根URL，再拼api/sessions和api/chat；不能从商城宿主页路径猜根。前端fetch明确credentials='same-origin'，不读取HttpOnly Cookie。代理保留Cookie、Authorization、Origin，禁用SSE缓冲；Agent上游端口只对可信代理开放。

新增唯一必要环境项AGENT_PUBLIC_ORIGIN，值为统一站点的scheme://host[:port]，不含路径。两个POST入口要求Origin精确匹配；缺失、null或不匹配一律403 ORIGIN_NOT_ALLOWED，不以Host/任意X-Forwarded-Host反推可信来源。GET健康检查与静态页面不适用此POST校验。非浏览器验收请求也必须显式提供正确Origin；这是跨站请求防护，不代替Bearer及商城身份校验。

不开放跨域CORS，不关闭商城原有CSRF，不把/users/csrf token加入聊天正文。商城登录/退出仍按原有CSRF协议调用。身份配置缺失/非法返回503 CONFIGURATION_ERROR，不启用静默匿名模式；/health保持现有存活语义，不冒充商城身份就绪探针。

## 6. 页面状态、旧流与宿主通知

复用现有sessionStorage token和AbortController，不加入前端登录态缓存。增加仅页面内的generation递增整数；每次请求捕获当前generation、本次controller和回复容器，异步回调不再从可被换掉的全局controller读取signal。

身份变化重置顺序必须为：generation加一 → abort旧请求 → 清除内存及sessionStorage token → 清空消息、输入、待显示动画、未读状态 → 展示新会话欢迎状态。下一次发送再懒创建新token；不把刚才消息自动重发到新身份。这是逻辑上立即新开聊天，避免未发消息就反复创建服务器记录。手动新会话复用这一重置语义；普通停止按钮仍保留本轮已显示内容。

所有会改变token或UI的异步路径都检查自己捕获的generation：创建会话成功、delta动画、error、catch和finally均包含在内。过期结果直接结束本地处理，不能保存旧token、追加旧回复、改掉新请求的busy状态。请求异常处理不能吞掉仍属当前轮的真实错误。

同域宿主通知约定：成功登录、退出、换号或当前登录被确认失效后，对客服iframe.contentWindow发送postMessage，内容仅{type:'mall:identity-changed', version:1}，targetOrigin精确指定当前origin。客服只接受event.origin===location.origin且event.source===window.parent的消息；顶层预览页中parent为自身，可用同结构通知验证。通知只触发清空和下次重新认证，不包含身份凭据，不授予权限。

客服收到合格父页面通知时同时向BroadcastChannel('xiaonuan.identity.v1')发布同结构消息；其它已打开客服页面收到后仅重置、不再次广播，防止循环。各页仍独立sessionStorage，不广播token、历史或用户ID。未打开客服的宿主页日后接入时也须发布该频道通知，确保其它已打开标签页获知登录变化；此责任写入宿主页任务，不假装当前已经接通。

HTTP 401 INVALID_SESSION或409 SESSION_IDENTITY_CHANGED触发同样的本页重置，并提示用户重新发送；不据单个无效token广播全站退出。503/502仅提示服务不可用，保留当前token和对话，不把故障当身份变化。身份事件打断旧流后，服务沿用现有断连取消与资源回收，不保证已发生的模型费用撤销。

明确边界：本期是“每次请求认证＋宿主通知后终止旧页面流”，不是商城端撤销事件实时推送。若商城后台在请求通过后禁用账号、但无通知，在途公开商品流可能继续至原截止时间；下一请求拒绝旧身份。真实宿主页未接入通知前，不能签署真实登录联动完成。订单等私有数据后续必须在业务接口再次由商城授权；不能把本阶段的入口检查当作订单授权。

## 7. 超时、资源与日志

商城身份查询最多1次/有效请求；无Cookie、非法Bearer或无归属记录为0次。首次带Cookie发消息通常包含创建会话和聊天两个HTTP请求，合计最多2次/users/me，不能报告成整个用户动作只有1次。登录用户后续每轮1次，不按token轮询；因此商城新增身份QPS约等于携Cookie的创建请求QPS＋有效聊天请求QPS。实际SQL/Redis次数取决于商城/users/me实现，不声称零数据库压力。

身份HTTP阶段墙钟等待上限5秒，urllib socket timeout同为5秒；最多4个在途身份HTTP操作，不排队，第5个立即503 IDENTITY_BUSY。复用现有受控同步任务的取消原则：请求停止等待后，同步线程未真正结束仍占槽位；真实结束后释放，不因wait_for取消而提前释放。身份查询不是商品tool，不占用原商品查询次数；不修改现有budget.py上限，不增加模型token。

归属IO每请求至多一次读取或一次插入，入口等待上限1秒。两段前置处理最长等待预算6秒，随后图仍受既有30秒预算约束；因此这是在原图预算之外增加前置预算，不声称整个HTTP请求仍为30秒。正常服务等待目标为前置6秒＋图30秒；不含浏览器逐字动画、网络背压及取消后的必要资源清理，不是生产SLO。

在现有日志体系新增identity_check和session_access结果字段：request_id、operation(create/chat)、结果类别、固定错误码、elapsed_ms；有已验签session_id时可沿用现有会话日志关联。正常guest、身份变化拒绝与依赖故障分别记录；不打印Cookie、Authorization、session_token、指纹、用户ID、上游正文或异常字符串。只记明确的异常类型。无需新观测平台、全局兜底或报警工程。
